# CMS-V2 performance masterplan

**Decision for the first sprint.** Give the student on a campus connection a faster path from opening CMS-V2 to taking the next action on their project. Start with the JavaScript and CSS every visitor gets. In parallel, measure the instructor dashboard during a submission rush. These are distinct delays with different fixes.

**Evidence as of 18 November 2026.** This plan uses the working tree based on `f63dae7`, the existing local production build and historical isolated benchmarks. The tree contains uncommitted changes. Browser timings for today's build, campus Wi-Fi timings and peak campus concurrency are still unknown. The figures below are proposed engineering budgets unless marked measured.

## Local production-build results after the startup refactor

On 18 November, Chromium exercised the preceding production build and the refactored build with the same assets, simulated signed-out API response, and a shared simulated 4 Mbps link with a 100 ms delay for each local asset request. Third-party requests were blocked. Each page has four observations per build, one for each combination of 1440×900 or 390×844 and light or dark mode. Each case opened the landing page followed by direct navigation to login with browser request interception. The timing endpoint was a visible landing heading or password input. These are local lab medians. They exclude real sign-in, campus network conditions, and server load.

| Measure | Previous build | Refactored build |
| --- | ---: | ---: |
| Assets referenced by entry HTML, raw bytes | 1,890,954 | 703,633 |
| Same assets, independently gzip-compressed at level 9, bytes | 522,859 | 199,224 |
| Landing heading visible, median | 3.24 s | 2.14 s |
| Login password field visible, median | 2.42 s | 1.59 s |

Vite now splits modules using their import relationships. PDF.js initializes with the viewer. The chart and PDF assets were absent from all eight refactored public-page checks. After loading the document viewer module in the production browser build, its PDF engine opened the sample document and rendered page one to a canvas. The initial HTML references 21 smaller assets, up from 15. The effect of this change on higher-latency campus networks still needs field measurement.

## What success looks like

p75 means three out of four experiences finish within the budget. Use p95 to see long waits during peak load. Each timing ends on something the user can see or do.

| Journey | Start → finish | Proposed budget |
| --- | --- | --- |
| First visit, cold browser | Open login → email field accepts input and submit control is ready | p75 ≤ 2.5 s on the reference mobile connection. Zero chart/PDF engine requests on plain login through 5 s after readiness. |
| Sign-in to dashboard | Submit valid credentials → correct role's primary action or actionable empty state is usable | p75 ≤ 2.0 s on campus Wi-Fi, ≤ 3.0 s on the reference mobile connection. Time external identity or OTP interaction separately. |
| Student project workspace | Tap “My Project” → correct project and current-phase action are usable | Warm p75 ≤ 1.0 s on campus Wi-Fi. A loaded navigation shell or skeleton does not stop the clock. |
| Instructor queue and archive search | Request queue or search → correct rows or confirmed empty result | API p95 ≤ 500 ms at agreed peak for each read. Archive results visible at p75 ≤ 1.5 s on campus Wi-Fi. |
| Manuscript review | Tap a document → first legible page at usable zoom | p75 ≤ 3.0 s on campus Wi-Fi for a specified 5 MB PDF. Report DOCX, scanned PDFs and 25–50 MB files separately. |
| Submission rush | Last upload byte received → durable acknowledgement with retrievable status | p95 ≤ 1 s on the asynchronous path. Dashboard API p95 during the rush ≤ 1.25× its idle baseline and unexpected 5xx < 1%. Record queue wait and total completion separately. |

Aim to halve the baseline p75 for the slowest common journey that misses its budget. If it already meets the target, move to the next largest measured wait. A faster acknowledgement only counts if the job survives a restart and the user can see the final outcome.

## How to run the comparison

1. **Select repeatable workloads.** Use Student, Instructor and Faculty test accounts through the official APIs. Include a student with a current project, faculty with multiple appointments, an instructor with 15 eligible projects, an empty archive search and a search with multiple pages. Include a small PDF, a scanned manuscript and a DOCX with revisions. Keep the dataset, selected files and role assignments identical between builds.
2. **Capture user time.** Use Playwright with `domcontentloaded` plus a locator for the usable action or first document page. For each priority case run 20 cold and 20 warm trials per build, interleaved where possible. Preserve medians, p75, raw samples, failed attempts, transferred bytes and request counts. Use a 390×844 viewport with a fixed lab profile (for example, 4 Mbps down, 1 Mbps up, 150 ms RTT and 4× CPU slowdown), then validate on a real phone and campus Wi-Fi. Record 1440×900 desktop separately.
3. **Capture server time.** Link a request ID to route duration, query count/time, payload size and queue job ID. Track CPU, resident memory, Node event-loop delay, Mongo pool wait, worker concurrency, oldest waiting job and completed jobs/minute. Keep identifiers and manuscript contents out of performance logs. Use browser network and server timing to identify the dominant stage before applying a cache or adding capacity.
4. **Reproduce peak load on an isolated deployment.** Start with illustrative 10, 30 and 60 active sessions using separate accounts, realistic pauses, and a read-heavy mix. Repeat the same workload with a submission burst. Replace these tiers with observed campus peaks once known. Collect at least 200 requests per critical read at the intended peak, plus errors, timeouts and completed work. Run bounded batches under the repo's two-minute command limit; keep the system state continuous when measuring backlog. Keep load traffic off the live campus system.
5. **Release one change at a time.** Ship frontend, query and worker changes separately. Pilot with a small cohort for one representative busy period. Roll back the affected release if a role sees incorrect data, work is lost or duplicated, a required gate unlocks early, or matched p95 worsens by more than 10% across two comparable windows. Keep queued jobs compatible during rollback. Run the repository's endpoint, governance, workflow and cleanliness checks before sign-off, plus the four light/dark desktop/mobile visual checks for client changes.

**First milestone:** a before/after login waterfall, a role dashboard that reaches its primary action faster, and an instructor query-count comparison. Use those results to choose between database work, worker isolation and network delivery improvements for the second sprint.
