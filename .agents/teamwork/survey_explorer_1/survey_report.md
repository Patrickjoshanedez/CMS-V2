## Executive Summary

An exhaustive audit of the BukSU CMS-V2 frontend (`client/src/`, encompassing 369 JSX files, CSS entry points, and backend deliverable services) was conducted across two primary domains:
1. **Track 1: UI Redesign, Sizing Optimization, Component Scaling, Spacing & Layout Integrity across all Views (R1)**
2. **Track 2: Capstone Lifecycle Paper Deliverables, Form Artifacts, and Printing Format Coverage (R3)**

### Core Findings at a Glance:
- **Paper Deliverable Gaps (R3):** While the Action Done Matrix (`ActionDoneMatrixTab.jsx`) and Secretary Minutes (`SecretaryMinutesDocumentSheet.jsx`) possess sophisticated `@media print` implementations, **the official Capstone 3 Final Approval Sheet (`approval-sheet.pdf`), generated by the backend and stored in archival storage, has NO frontend consumer or presentation UI in `client/src`**. Furthermore, **Defense Evaluation Rubrics (`EvaluationPanel.jsx`)**, **Gantt Chart Schedules (`InteractiveGanttChart.jsx`)**, **Proposal Title Defense Endorsement Sheets (`TitleApprovalPage.jsx`)**, and **Department Defense Scheduling Calendars (`DefenseSchedulingPage.jsx`)** completely lack print stylesheets or printable views. The canonical document reader (`SophisticatedDocumentViewer.jsx`) has **no print button or print unrolling**, causing manuscripts to clip within scroll wrappers upon browser printing. `PlagiarismReportPage.jsx` has a Print button that calls `window.print()` but lacks `@media print` rules, causing UI buttons and sidebars to bleed into printouts.
- **UI Sizing, Spacing & Layout Gaps (R1):** The default layout container (`DashboardLayout.jsx`) enforces `max-w-7xl` (`1280px`), but several components introduce arbitrary constraints (e.g., `CanonicalDocumentViewer.jsx` forces `max-w-5xl`, restricting viewer width on 1440x900 viewports; `VersionHistory.jsx` forces `max-w-6xl` with `max-h-[calc(100dvh-2rem)]`, which overflows viewports < 1200px). Radix Dialogs (`Dialog.jsx`) lack print unrolling and background overlay suppression (`print:hidden`), causing dialogs printed via `window.print()` (`LiveDefenseMinutesModal.jsx`) to print as fixed, clipped cards pinned to page 1. Multiple interactive controls lack the mobile 44px touch target floor (`min-h-[44px]`), 17 forms lack Cowan 4-chunk semantic `<fieldset>` partitioning, and 6 tables lack responsive `overflow-x-auto` wrappers. `CanonicalDocumentViewer.jsx` violates the single `<h1>` modern web standard by rendering two `<h1>` tags.

### 1.2 In-Depth Analysis of Print Deficiencies & Gaps

#### 1.2.1 Critical Finding: Unexposed Final Approval Sheet (`approval-sheet.pdf`)
- **Backend Evidence:** In `server/modules/projects/services/projectArchive.service.js` (lines 130–180 and 709–714), the system automatically constructs an official BukSU Capstone 3 Final Approval Sheet using `pdf-lib` upon archival sign-off, containing university headers, project metadata, student author names, four-tier digital signatures (Adviser, Chair, Panelists, Dean), and SHA-256 verification hash. The signed document is stored at `archives/projects/{projectId}/approval/approval-sheet.pdf`.
- **API Endpoint:** `GET /api/projects/:id/approval-sheet` (mapped in `server/modules/projects/project.routes.js:530` and `project.controller.js:661`).
- **Frontend Defect:** In `client/src/services/authService.js:241`, `getApprovalSheetUrl: (id) => api.get('/projects/' + id + '/approval-sheet')` is exported. However, **not a single component or page in `client/src` imports or invokes `getApprovalSheetUrl`**. On `CertificatePage.jsx`, `ProjectSubmissionsPage.jsx`, and `ActionDoneMatrixTab.jsx`, there is no button or card enabling students, advisers, or instructors to view, download, or print this document.
- **Remediation:**
  1. Add a dedicated hook `useApprovalSheetUrl(projectId)` in `client/src/hooks/useProjects.js`.
  2. Embed an "Official Final Approval Sheet" card alongside the Completion Certificate on `CertificatePage.jsx` and in `ActionDoneMatrixTab.jsx` (when Tier 3 signatures are complete), providing direct View in `SophisticatedDocumentViewer`, Download, and Print actions.

#### 1.2.2 Critical Finding: Document Viewer (`SophisticatedDocumentViewer.jsx`) Lacks Print Capabilities
- **Direct Observation:** `client/src/components/documents/SophisticatedDocumentViewer.jsx` contains 1,796 lines of code supporting OOXML `docx-preview`, PDF viewing, and revision diffing. However, a grep for `print` yields **0 matches**. The toolbar contains `Download`, `Zoom`, `Fullscreen`, and `Diff`, but **no Print button**.
- **Print Overflow Failure:** Line 1727 wraps the rendered document in:
  ```jsx
  <div className="flex-1 overflow-auto bg-muted">
    <div className="docx-zoom-wrapper w-max min-w-full origin-top-left" style={{ zoom: zoom / 100 }}>
      <div ref={containerRef} className="docx-outer-container" />
    </div>
  </div>
  ```
  When a user triggers browser print (Ctrl+P) while viewing a manuscript:
  1. The `overflow-auto` container clips the document to the visible viewport height (~700px), causing all subsequent pages to be dropped.
  2. The toolbar, identity header, zoom sliders, and background gray canvas (`bg-muted`) print verbatim.
  3. The `zoom` CSS property distorts printed page metrics.
- **Remediation:**
  1. Add a `Printer` icon button to the `SophisticatedDocumentViewer` toolbar with `onClick={() => window.print()}`.
  2. Add `@media print` rules in `index.css`:
     ```css
     @media print {
       .sophisticated-viewer-toolbar,
       .sophisticated-viewer-identity-bar,
       .sophisticated-viewer-diff-sidebar {
         display: none !important;
       }
       .docx-outer-container,
       .docx-outer-container .docx-wrapper {
         overflow: visible !important;
         height: auto !important;
         max-height: none !important;
         background: transparent !important;
         padding: 0 !important;
       }
       .docx-outer-container .docx-wrapper > section.docx {
         box-shadow: none !important;
         margin: 0 0 20mm 0 !important;
         break-after: page !important;
         page-break-after: always !important;
       }
     }
     ```

#### 1.2.4 High Severity: Radix Dialog Modal Clipping During Print (`LiveDefenseMinutesModal.jsx`)
- **Direct Observation:** `client/src/components/defense/LiveDefenseMinutesModal.jsx:606` contains:
  ```jsx
  <Button variant="outline" size="sm" onClick={handlePrint}>
    <Printer className="h-3.5 w-3.5" />
    Print Form
  </Button>
  ```
  The component is wrapped inside Radix UI's `DialogContent` (`client/src/components/ui/Dialog.jsx:39`):
  ```jsx
  className="dialog-centered fixed left-1/2 top-1/2 z-50 grid grid-cols-1 max-h-[min(90vh,48rem)] w-[calc(100vw_-_2rem)] min-w-0 max-w-lg gap-4 overflow-y-auto rounded-lg ..."
  ```
  and `DialogOverlay` has `fixed inset-0 z-50 bg-overlay/60 backdrop-blur-[2px]`.
- **Print Failure Mode:**
  When `window.print()` is executed from inside a modal:
  1. The `DialogOverlay` renders a dark 60% gray veil across the entire print sheet.
  2. The `DialogContent` remains `fixed` at `top: 50% left: 50%` with `max-h-[90vh]` and `overflow-y-auto`. As a result, the browser prints only the first ~800 pixels of the dialog. All subsequent agenda minutes, panel remarks, and signature blocks are completely clipped.
- **Remediation:**
  Add global dialog print rules to `client/src/index.css`:
  ```css
  @media print {
    [data-radix-dialog-overlay],
    .dialog-overlay {
      display: none !important;
    }
    body:has([role="dialog"]) [role="dialog"] {
      position: static !important;
      left: auto !important;
      top: auto !important;
      translate: none !important;
      transform: none !important;
      max-height: none !important;
      width: 100% !important;
      max-width: 100% !important;
      overflow: visible !important;
      box-shadow: none !important;
      border: none !important;
      padding: 0 !important;
      background: white !important;
      color: black !important;
    }
    body:has([role="dialog"]) > *:not([data-radix-portal]) {
      display: none !important;
    }
  }
  ```

### 2.2 Mobile Touch Target Normalization (< 44px Floor Violations)

WCAG 2.1 Success Criterion 2.5.5 (Target Size) and WCAG 2.2 Success Criterion 2.5.8 (Target Size Minimum) require that interactive touch targets be at least 44×44px on mobile viewports. On desktop viewports (`sm:`), components may scale to compact desktop density (`h-8`, `h-7`).

The following buttons violate this standard by hardcoding small heights without mobile floor styling:

1. **`client/src/components/projects/ActionDoneMatrixTab.jsx:826`**
   - *Current Code:* `<Button size="sm" onClick={handleAddRow} className="gap-1.5 text-xs h-8">`
   - *Defect:* `h-8` (32px) on mobile viewports makes adding ADM recommendation rows difficult to tap on mobile devices (390x844).
   - *Fix:* `className="min-h-[44px] sm:min-h-0 sm:h-8 gap-1.5 text-xs"`

2. **`client/src/components/projects/PrototypeGalleryModal.jsx:147`**
   - *Current Code:* `<Button size="sm" asChild className="h-8 text-xs gap-1.5">`
   - *Defect:* External prototype launch button is 32px high on touch screens.
   - *Fix:* `className="min-h-[44px] sm:min-h-0 sm:h-8 text-xs gap-1.5"`

3. **`client/src/components/teams/ManuscriptTemplateWidget.jsx:117 & 205`**
   - *Current Code:* `<Button asChild variant="outline" size="sm" className="h-8 shrink-0 gap-1 text-xs">`
   - *Defect:* Google Docs manuscript launch and copy buttons are 32px on touch viewports.
   - *Fix:* `className="min-h-[44px] sm:min-h-0 sm:h-8 shrink-0 gap-1 text-xs"`

4. **`client/src/components/teams/TeamFormationNotificationItem.jsx:251`**
   - *Current Code:* `<Button size="sm" className="h-8 gap-1.5 text-xs" onClick={handleAssign}>`
   - *Defect:* Committee quick-assign button is 32px on mobile notifications.
   - *Fix:* `className="min-h-[44px] sm:min-h-0 sm:h-8 gap-1.5 text-xs"`

5. **`client/src/pages/submissions/SubmissionReviewPage.jsx:947 & 955`**
   - *Current Code:* `<Button asChild variant="outline" className="w-full gap-2 text-xs h-8">`
   - *Defect:* Chapter review quick-jump actions are 32px high on touch viewports.
   - *Fix:* `className="min-h-[44px] sm:min-h-0 sm:h-8 w-full gap-2 text-xs"`

### 2.3 Form Chunking & Cognitive Ergonomics (Cowan 2001 Working Memory Limit)

According to `cognitive-ergonomics-ux`, forms with more than 3–4 inputs must be partitioned into semantic `<fieldset>` groups with `<legend>` headers to maintain cognitive ergonomics and meet WCAG 2.2 AA standards. The audit identified **17 unchunked forms**:

1. **`client/src/pages/users/UsersPage.jsx` (`CreateUserForm`, lines 1327–1375):**
   - Contains 6 inputs (`firstName`, `middleName`, `lastName`, `email`, `password`, `role`) in a flat `<form className="space-y-4">`.
   - *Remediation:* Partition into two `<fieldset>` groups:
     - Group 1: `<legend className="text-xs font-semibold text-muted-foreground uppercase tracking-wider">Personal Identity</legend>` (First, Middle, Last Name).
     - Group 2: `<legend className="text-xs font-semibold text-muted-foreground uppercase tracking-wider">Account Credentials & Access</legend>` (Email, Password, Role).
2. **`client/src/pages/archive/ExistingCapstoneUploadPage.jsx` (lines 1450–1750):**
   - Contains 12 metadata inputs (Title, Abstract, Authors, Year, DOI, Venue, Keywords, Academic Year, etc.) in a long vertical list without `<fieldset>` partitioning.
   - *Remediation:* Partition into three semantic fieldsets:
     - Fieldset 1: *Document Publication Identity* (Title, Authors, Publication Year, Academic Year).
     - Fieldset 2: *Content Abstract & Classification* (Abstract, Keywords, Disciplines, SDG Tags).
     - Fieldset 3: *Bibliographic Citations* (DOI, Publication Venue, Publisher).
3. **`client/src/pages/profile/ProfilePage.jsx` (lines 350–550):**
   - Contains 9 inputs across personal identity, student academic bindings (Student ID, Term, Section, Instructor), and system thresholds in a single card body.
   - *Remediation:* Partition into semantic `<fieldset>` sections with `<legend>` headers.
4. **`client/src/components/defense/ScheduleDefenseModal.jsx` (6 inputs):**
   - Partition into *Hearing Timeslot & Venue* and *Committee Panel Confirmation*.
5. **`client/src/components/instructor/MilestoneDeadlinesModal.jsx` (6 inputs):**
   - Partition into *Milestone Phase Binding* and *Target Due Dates & Grace Periods*.
